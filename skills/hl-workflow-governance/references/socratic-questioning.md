# Socratic Questioning

This is the shared questioning policy for the entire factory workflow, including initialization,
feasibility, decomposition, Feature discussion, quick changes, implementation clarifications,
review, verification, maintenance and optional packs. It applies to chat, choice panels and
questions written into a workbench. Read it before asking the user a workflow question.

## Method

- Inspect available evidence first. Do not ask the user to rediscover repository facts.
- Start from the user's stated goal and latest answer. Ask one focused, neutral question that
  resolves the most consequential uncertainty; briefly explain why the answer matters.
- Choose the useful line of inquiry: clarify a concept or concrete example; surface an
  assumption; examine evidence and a counterexample; consider another perspective or alternative;
  trace consequences and tradeoffs; or examine the success criterion or the question itself.
  These are tools, not a mandatory sequence or a checklist to exhaust on every topic.
- Follow the answer: distinguish observation from inference, test the relevant premise, then
  help the user state a conclusion and its boundary. Challenge ideas respectfully; do not use
  rhetorical questions, interrogation, false dilemmas or questions designed to win agreement.
- Offer facts and explanations directly when needed. Do not withhold an answer to turn every
  exchange into a lesson. Recommendations must be evidence-based, conditional and separate from
  the question; explain what could overturn them. Never embed the desired answer in the wording.
- Stop probing once the required uncertainty is resolved. Reuse explicit answers and existing
  authorization; do not reopen settled decisions without new evidence or request new approval
  solely to satisfy this style. Silence, an agent inference and a recommendation are not consent.

## Delivery and authorization

Interactive discussion asks one question and waits for its answer before a dependent follow-up.
For a real choice, use the available structured choice panel with 2-3 viable, neutrally described
options and custom input. When the tool requires a recommendation first, mark it as required by
the tool and explain its conditional basis without making alternatives sound invalid. For an
open exploration of meaning or evidence, use a free-text question rather than inventing options.

An explicitly chosen batch-review mode may present several independent Socratic questions in
the workbench. Each block states the known context, one open question, the premise or evidence
being tested and the decision impact; add alternatives or a conditional recommendation only when
useful. Do not fabricate follow-up answers or decide dependent questions before the user replies.
Keep confirmed conclusions, proposals and unresolved questions distinct.

Required authorization remains a direct, explicit request identifying the concrete action,
scope and material consequences. Do not substitute exploratory dialogue for permission or infer
permission from a user's answer about goals. Missing required input or approval keeps the
dependent action blocked under its existing gate; this policy adds no new lifecycle gate.

## Examples

- Clarification: "When you say 'fast enough', which user action and observable delay define success?"
- Assumption: "What makes immediate consistency necessary in this scenario?"
- Evidence: "Which observed failure supports that explanation?"
- Counterexample: "What happens to that rule when the same request arrives twice?"
- Perspective: "How would an operator recover if this dependency were unavailable?"
- Consequence: "If we retain this data, what recovery obligation follows?"

Use the relevant question, then follow the actual answer; do not send this list as an interview.
