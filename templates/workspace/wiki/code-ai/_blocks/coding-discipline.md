# Block：编码纪律

> 类型：项目级通用约束 · 适用：所有实现与验证

本块回答一个与“测什么”不同的问题：**写的时候按什么顺序、遵守什么纪律，才算把活干完。**

三段顺序不可交换：

1. **先让它对**——能跑通，且能用证据证明它是对的。
2. **再让它干净**——结构、复杂度、重复、死代码都处理掉。
3. **收尾习惯**——日志、上下文、清理、提交。

跳过第一段直接美化结构，或做完第二段却不留下收尾痕迹，都视为未完成。

## 1. 先让它对

### 决策只存一处

- 同一个业务判断只在一处实现。发现第二处等价判断，就是缺陷，不是“经验复用”。
- 需要复制才能复用，说明抽象边界错了；先改边界，再复用。

### 先定数据形状，再写逻辑

- 写流程之前先确定数据的形状与合法状态；让非法状态在结构上无法表达，而不是靠运行时断言兜住。
- 一次只把一件事放到正确的位置：先做那个能让后面所有步骤都变简单的事。
- 顺序判断依据：这件事做完之后，剩下的步骤是否变短、变少或变得可检验。

### TDD 顺序

1. 先写会失败的测试。
2. 确认它**因为预期的原因**失败，而不是因为写错或环境问题。
3. 再写让它变绿的最小改动。
4. 如果写不出诚实的测试，就不要写一个假的：说明为什么无法测、用什么证据替代，并让评审看见这个缺口。

只补测试不改顺序（先写实现后补测试）不算 TDD，最多算回归覆盖；在交接里必须如实区分。

### 从第一性原理重设计

- 不要给旧设计外挂新需求。
- 先问：如果从一开始就有这个需求，我会建成什么样？把它想清楚，再分片交付。
- 分片交付不等于临时拼装：每一片都要能独立验证，且不把系统留在半新半旧的状态。

### 攻击前提

- 当两个共享同一前提的修法以同样的方式失败，先停下修法。
- 把那个前提写成一句话，数清有多少人、多少模块在为它付出代价。
- 移除那个前提或那个赋值，然后再开始下一个修复。
- 不允许“再试一个补丁看看”式推进。

### 先减后加

- 任何新增之前先问：能删掉什么？能合并什么？
- 新增的复杂度必须小于或等于它消除的复杂度；否则先做减法。
- “以后可能会用”不是保留理由。

### 面向可检验的终态

- 开工前明确终态：做完之后能检查什么。
- 中途允许不可运行，但必须是你计划内的、可回退的一步，并在交接里写明当前处于哪一步。
- 不以“代码已经写了”作为进度，只以可检验状态作为进度。

### 造杠杆

- 如果这件事不是一眼能做完的，先造做这件事的工具。
- 先手工完成一个单元，再让工具对齐那个单元的输出；不要先造通用工具再找用例。
- 工具本身也要有一条命令能验证它做对了。

### 共享状态

- 不需要共享的可变状态，就不要共享：各自持有自己的。
- 必须共享时，只允许一个写者，并在结构上强制这一点（不是靠约定或注释）。

## 2. 再让它干净

### 修根因

- 先复现，再改因。
- 只遮住崩溃的守卫、只绕过失败分支的补丁，都不算修复。
- 修复后必须能让原来的复现步骤变绿，且不引入新的红灯。

### 切成可验证单元

- 完成一小步就验证，再开始下一步。
- 不允许长时间停留在“写完了但没验证”的状态。
- 一次提交对应一个可验证单元，不做“先把所有东西改完再一起跑”。

### 测行为不测实现

- 测试要像它的使用者那样调用代码，检查使用者能看到的结果。
- 如果所有函数都返回空值、测试仍然通过，这个测试应当删除。
- 不为了测试而在生产代码里加入特权分支、后门或仅测试可见的状态。

### 定量质量门

以下三项只有在项目启用 `$hl-quality-gates` 且配置了对应工具时才生效；未启用时按项目自己的测试与评审标准执行，不得反过来要求项目先安装工具。

- **复杂度**：每个函数的 CRAP 必须低于配置的阈值（默认 10）。超标只能通过拆分或补测解决，不许调阈值。
- **重复**：相似度达到或超过配置阈值（默认 0.8）的结构重复必须消除；无法消除时必须书面说明为什么保留，并由评审接受。工具只产出候选，判定不在工具。
- **变异**：基线测试必须先通过才能运行；存在存活变异是 Blocker，未覆盖代码计为未覆盖，不算通过。

定量结果一律以证据文件为准，不以“我本地跑过”为准；没有证据的性能或复杂度声明按未验证处理。

### 重构三步

1. 固定当前行为：有测试或等价证据能证明现在的行为。
2. 改变结构：只改结构，不夹带行为变更。
3. 证明行为未变：同一个证据在重构前后一致。

三步中任一步没有证据，都不算完成重构。重构与功能变更不得混在同一次提交里。

### 边界与类型

- 外部数据只在入口校验一次；进入内部后信任它，不要在每一层重复校验。
- 业务逻辑尽量放在可独立测试的纯函数里。
- 不静默编译器或类型检查器：不用强制转换、忽略注释或动态逃逸来消除报警。
- 越界的值应当在类型或结构上不可写，而不是靠运行时报错。

### 幂等

- 重复执行，或在执行到一半崩溃后重跑，终态必须相同。
- 涉及写入、迁移、回填、外部副作用时，幂等性是必须项，不是可选优化。

### 死代码即缺陷

- 为让测试通过而保留的死代码、不可达分支、永假条件必须删除。
- 注释掉的旧实现、调试残留、“暂时保留”的开关，在交付前清除或登记为待办并写明责任人。

## 3. 收尾习惯

### 日志

- 按 [_blocks/agent-notes-rule.md](agent-notes-rule.md) 记录每一次动作与原因。
- 完成时把日志汇总进交接，使用 [_blocks/handoff-output.md](handoff-output.md) 的固定结构。
- 日志是给下一个人用的证据，不是给自己看的草稿。

### 上下文

- 主 agent 或主线程只保留判断、决策与结论；大体量的阅读、检索与实现外包出去，只收回摘要与证据位置。
- 不在主线程整篇通读大文件；用定向检索和分段阅读。
- 派发任务时给最小充分上下文，不要把整份历史塞给执行者。

### 清理

- 临时脚本、一次性 worktree、构建与度量残留，在确认无用后回收；回收前先确认没有未提交工作或仍在使用。
- 未提交的工作必须等人类决定，不得自行丢弃、stash 或强制删除。
- worktree 与分支的清理规则见 `$hl-workflow-governance` 的 worktree 生命周期参考，本块不重复定义。

### 小步提交

- 粒度与顺序见 [_blocks/commit-granularity.md](commit-granularity.md)。
- 每个提交说明三件事：为什么改、改了什么、怎么证明它是对的。
- 提交授权不等于推送授权。

## 交付前自检

- [ ] 每个业务判断只存在一处实现，没有复制出来的等价判断。
- [ ] 数据形状与合法状态在写逻辑之前已经确定。
- [ ] 新行为有先红后绿的测试；无法测的原因与替代证据已写明。
- [ ] 没有把新需求外挂在旧设计上；共享可变状态只有一个写者。
- [ ] 改的是根因，不是遮住崩溃的守卫。
- [ ] 消除的复杂度不少于新增的复杂度，或有书面理由。
- [ ] 若启用 `$hl-quality-gates`：复杂度、重复、变异三项都有对应证据文件且结论一致。
- [ ] 死代码、调试残留、临时脚本已清除或登记。
- [ ] 日志与交接按 agent-notes-rule 与 handoff-output 维护。
- [ ] 提交粒度与授权边界符合 commit-granularity。

## 与项目规则的关系

- 本块给出通用下限。项目可以加严（更低的 CRAP 阈值、更严的重复判定、必跑的变异范围），但不得以减少步骤为由放宽上述任一条件。
- 与 [_blocks/testing-quality-gate.md](testing-quality-gate.md) 的分工：本块定义**怎么写、按什么顺序写**；该块定义**测什么、测到哪一层**。两者都要满足。
- 与 [_blocks/common-definition-of-done.md](common-definition-of-done.md) 的分工：本块是过程中的纪律，该块是关闭前的完成定义。本块的自检项不替代完成定义。
- 规则冲突时先停止并升级，不得静默取舍。
