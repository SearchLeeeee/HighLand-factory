# Block：日志与诊断

> 类型：项目级通用约束 · 适用：所有运行时、脚本与测试辅助代码

## 目的

让问题可定位、可复现、可解释，同时不把敏感信息带进日志。

## 分级

- Error：需要人介入的失败，包含可定位上下文。
- Warn：可恢复异常、降级、重试耗尽前的异常信号。
- Info：关键业务或生命周期节点，数量可控。
- Debug：开发诊断，默认不常开，不得成为唯一证据来源。

级别要稳定：同一事件不得在不同路径使用不同级别。

## 结构化与上下文

1. 优先输出结构化字段（时间、级别、组件、操作、结果、耗时、关联标识），而不是拼字符串。
2. 关键路径要有可串联的关联标识，便于跨模块追踪。
3. 错误日志必须包含失败原因与可执行的下一步线索，不能只写“失败”。
4. 不在循环内输出高频 Info；必要时聚合或采样。
5. 日志文本不承载业务语义判断；代码逻辑不得依赖日志字符串。

## 脱敏与安全

- 不记录凭据、令牌、会话、完整个人数据或生产连接串。
- 不记录完整请求体或响应体；必要时只记录白名单字段与长度。
- 异常对象可能携带敏感内容，输出前必须过滤。
- 调试开关不得在生产默认开启，也不得成为绕过权限的入口。

## 诊断质量

- 失败路径要能区分：输入错误、依赖不可用、超时、部分失败、权限拒绝。
- 重试要记录尝试次数与最终结果，避免“静默重试”。
- 可观测性改动也要有测试或可验证证据，不能只靠人工观察。
- 日志与指标、追踪的职责要分清，避免重复或互相矛盾。

## 自检

- [ ] 关键失败都能从日志定位到组件与操作。
- [ ] 没有敏感字段进入日志或异常信息。
- [ ] 级别使用一致，没有高频刷屏。
- [ ] 诊断改动有对应验证方式。
