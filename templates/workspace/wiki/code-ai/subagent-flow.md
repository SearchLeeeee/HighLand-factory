# 子代理四角色流程

本页定义与具体项目无关的四角色协作流程：**阅读（Reading）→ 实现（Implementation）→ 评审（Review）→ 验证（Verification）**。流程只约束顺序、交接与停止条件，不约束具体技术栈。

## 1. 角色与职责

| 角色 | 核心职责 | 不得做的事 |
| --- | --- | --- |
| 阅读 | 建立事实基线：权威来源、范围、约束、风险、实现入口 | 修改文件、替项目做决定、把推测写成事实 |
| 实现 | 在批准的计划与写入范围内完成最小改动 | 扩大范围、绕过评审、自行判定契约 |
| 评审 | 独立检查正确性、契约、安全、测试与文档同步 | 直接改代码、被实现角色“口头说服”后放行 |
| 验证 | 以可复现证据确认验收项，记录残余风险 | 用“看起来没问题”替代证据、重跑实现 |

同一会话不得同时充当实现与最终评审；评审必须独立（见 [review-agent.md](review-agent.md)）。独立性要求独立判断，不默认重跑全部检查或重建环境；验证范围以实际改动及其影响为准，复用未变化且仍适用的结果，同一事实不叠加等价校验。主编排核对关键证据并按实际风险抽查。

## 2. 编排顺序（固定）

`intake → preflight → goal → source survey / plan proposals → integrated plan → implementation → review → verification/acceptance → closure → commit（仅在被授权时）`

| 阶段 | 产出 | 退出条件 |
| --- | --- | --- |
| intake | 任务陈述、干系人、期望 | 任务可被一句话说清 |
| preflight | 权威来源、范围、风险、缺口 | 无阻塞性缺口，或缺口已被显式记录 |
| goal | 目标、验收标准、非目标 | 验收标准可被验证 |
| source survey / plan proposals | 阅读交接与各 owner 的只读 plan proposal；列出代码事实、候选文件、依赖和验证 | 资料足以形成整 Feature 计划，或缺口已明确升级 |
| integrated plan | 唯一 Feature 计划 `<feature-root>/code-ai/implementation-plan.md`，按 [implementation-plan-template.md](implementation-plan-template.md) 记录 owner/file map、顺序、依赖、验收、条件风险和有意义的集成检查点 | 主编排者批准；用户需要决定的事项已解决；所有 worker scope 来自获批计划 |
| implementation | 按已分配的 plan item 实现并在原位验证，超出计划时停止受影响部分 | 计划项完成并交付证据；必要的里程碑或集成检查通过 |
| review | 评审报告与发现级别 | 无 Blocker/High，或已获明确处置 |
| verification/acceptance | 证据、覆盖情况、结论 | 验收项全部有证据或明确未覆盖 |
| closure | 关闭说明、遗留项、同步清单 | 无未登记遗留项 |
| commit | 提交与推送（如授权） | 授权明确、提交粒度合规 |

任一阶段发现需要改变目标、验收标准、契约或写入范围时，回到对应阶段，不得在实现中偷偷改目标。

计划格式的唯一来源是 [implementation-plan-template.md](implementation-plan-template.md)。阅读角色可在计划创建前调查代码并提出计划建议，但不得修改业务逻辑。主编排者结合实际代码调研和各 owner 的 plan-only proposal，维护一份整 Feature 计划；不得为每个 worker 复制一份主计划。计划须在第一个实现文件改动前获批。计划深度按风险选择：有界单 owner 工作可以短一些；跨 owner、共享契约、schema/state、数据迁移、安全或高风险行为需要按模板填写条件章节。

并行 item 必须依赖已满足，且文件范围和契约范围都不重叠。计划安排必要的集成验证点，最终集成由主编排者负责。每个实现步骤仍在原位验证；相同模型/会话不必为每个微步骤写重复 handoff。仅在有意义的里程碑、多 agent 汇合、高风险变化或重大偏差时做简短检查点。重大范围、契约、安全或产品决策停下升级；获批的实现调整更新同一份计划并批准受影响部分后继续。

## 3. 阅读交接（固定标题）

阅读角色必须输出以下固定标题，缺一不可：

### 阅读交接：范围
任务边界、涉及模块、明确不做什么。

### 阅读交接：权威来源
列出被采信的文档与代码位置，并说明为何采信；列出被判定为过期或非权威的来源。

### 阅读交接：事实与约束
与任务直接相关的稳定事实、接口契约、数据归属、适用约束块。

### 阅读交接：风险与未决问题
风险类别、影响面、需要谁确认；未决问题不得用假设替代。

### 阅读交接：实现入口
建议的最小实现路径、首个改动点、需要的验证方式。

阅读交接只描述事实与建议，不包含实现改动；交接使用 [_blocks/handoff-output.md](_blocks/handoff-output.md) 的通用结构承载细节。

## 4. 实现交接

实现角色按 [_blocks/handoff-output.md](_blocks/handoff-output.md) 的固定结构输出，必须包含：改动清单、行为变化、验证证据、未决问题、回滚方式、需要评审重点看的部分。实现交接不得声称“已评审通过”。

## 5. 评审交接

评审角色必须拿到当前批准的 `implementation-plan.md`，核对改动是否符合获批 scope、owner/file 边界、依赖和集成安排；计划与实际不一致，或评审期间计划的语义变化影响当前判断时，停止受影响部分并交还主编排者处理；单纯记录或非语义性更正不自动使其他有效结论失效。之后按 [review-agent.md](review-agent.md) 与 [_blocks/review-agent-contract.md](_blocks/review-agent-contract.md) 的固定报告结构输出，明确结论、发现级别、未覆盖项与复审建议。

## 6. 验证交接（固定标题）

验证角色必须输出以下固定标题，缺一不可：

### 验证交接：验证对象
被验证的变更标识、环境、基线与范围。

### 验证交接：验收项覆盖
逐条列出验收项、对应证据、通过/失败/未覆盖；不得合并模糊描述。

### 验证交接：证据
可复现的证据位置与复现方式；证据不足时明确写“证据不足”。

### 验证交接：未覆盖与残余风险
未覆盖项、环境差异、已知限制、需要后续跟踪的事项。

### 验证交接：结论
通过、有条件通过、不通过；有条件通过必须列出条件与责任人。

验证交接不得修改被验证对象；发现问题回到实现或评审阶段。
验证角色使用同一份当前批准计划，逐项确认计划结果和 Feature 验收标准都有可复现证据。默认用 Git revision 加相关 diff / 新增文件内容识别对象，保持来源稳定，不强制预提交、全树 clean、新 clone、逐文件摘要或额外 receipt；未授权提交不妨碍评审和验证可识别的未提交内容。来源变化只重新检查受影响结论，单纯 HEAD、证据或生命周期记录变化不自动失效；只有实际来源歧义、污染、并发冲突或制品完整性需要时，简短说明风险并增加必要的内容固定、隔离或摘要，不增加额外审批。

局部失败或材料缺口先诊断，只补受影响部分，保留其他有效结果。保留必要的执行结果与失败记录，产生原始日志时与可清理的测试 output 分开保存，不默认对日志或全部证据计算摘要；如实保留失败和未执行项。非语义性格式或文字更正可说明，不迫使重建整套证据。满足既定验收和交付边界即停止，不递归证明已有证据；明确验收要求的实际执行仍须完成。

## 7. 冲突处理

- **权威冲突**：两份文档对同一契约给出不同答案时，停止实现，列出冲突点、各自出处与影响，交人类裁决。
- **范围冲突**：任务要求越过 owner 写入范围或项目边界时，停止并转交对应 owner，不自行扩权。
- **评审冲突**：实现与评审对事实判断不一致时，以可复现证据为准；证据不足则升级，不以角色级别压人。
- **验收冲突**：验收标准不可验证或互相矛盾时，回到 goal 阶段重写标准，不得降低标准换取通过。
- **时间冲突**：无法在约束内完成时，优先保证正确性与可回滚性，显式记录未完成项，不交付“看起来完成”的结果。

所有冲突都必须留下书面记录，并写明当前阻塞点与所需决策。
