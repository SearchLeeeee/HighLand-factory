# 子代理四角色流程

本页定义与具体项目无关的四角色协作流程：**阅读（Reading）→ 实现（Implementation）→ 评审（Review）→ 验证（Verification）**。流程只约束顺序、交接与停止条件，不约束具体技术栈。

## 1. 角色与职责

| 角色 | 核心职责 | 不得做的事 |
| --- | --- | --- |
| 阅读 | 建立事实基线：权威来源、范围、约束、风险、实现入口 | 修改文件、替项目做决定、把推测写成事实 |
| 实现 | 在批准的计划与写入范围内完成最小改动 | 扩大范围、绕过评审、自行判定契约 |
| 评审 | 独立检查正确性、契约、安全、测试与文档同步 | 直接改代码、被实现角色“口头说服”后放行 |
| 验证 | 以可复现证据确认验收项，记录残余风险 | 用“看起来没问题”替代证据、重跑实现 |

角色独立性遵循[_blocks/review-gate.md](_blocks/review-gate.md)；最小充分验证、证据复用和失败处置统一见[_blocks/testing-quality-gate.md](_blocks/testing-quality-gate.md)。本页只说明各角色如何应用。

## 2. 编排顺序（固定）

`intake → preflight → goal → source survey / plan proposals → integrated plan → implementation → review → verification/acceptance → closure`

下表中的 Feature 计划要求适用于 Feature 开发。用户明确发起的 `hl-refactor` 手动维护保留相同四角色职责、全部通用必读和 owner 边界，以本轮运行记录中的扫描范围、候选、用户选择、依赖、精确文件范围、验收和证据作为统一任务依据。它不创建 Feature 或 Feature profile，不要求虚构 `implementation-plan.md`；只读扫描无需实施计划，修改必须先通过维护准入、占用和候选选择。独立评审同时完成简短只读接续检查，证据可在一份报告中引用，不要求额外功能或重复报告。

| 阶段 | 产出 | 退出条件 |
| --- | --- | --- |
| intake | 任务陈述、干系人、期望 | 任务可被一句话说清 |
| preflight | 权威来源、范围、风险、缺口 | 无阻塞性缺口，或缺口已被显式记录 |
| goal | 目标、验收标准、非目标 | 验收标准可被验证 |
| source survey / plan proposals | 当前可用的代码走查和必要 owner 的只读 plan proposal；列出现状事实、候选文件、依赖与验证 | Feature 由整合者形成计划；手动维护形成证据与成本明确的候选。缺事实先澄清 |
| integrated plan | Feature 使用唯一 `<feature-root>/code-ai/implementation-plan.md`，按 [计划模板](implementation-plan-template.md) 记录 owner/file map、顺序、依赖、验收、条件风险和有意义的集成检查点；手动维护使用同一运行记录中的已选候选、顺序与实施范围 | 主编排者批准；用户需要决定的事项已解决；所有 worker scope 来自对应获批依据 |
| implementation | 按已分配的 plan item 实现并在原位验证，超出计划时停止受影响部分 | 计划项完成并交付证据；必要的里程碑或集成检查通过 |
| review | 评审报告与发现级别 | 无 Blocker/High，或已获明确处置 |
| verification/acceptance | 证据、覆盖情况、结论 | 验收项全部有证据或明确未覆盖 |
| closure | 关闭说明、遗留项、同步清单 | 无未登记遗留项 |

任一阶段发现需要改变目标、验收标准、契约或写入范围时，回到对应阶段，不得在实现中偷偷改目标。

Feature 计划格式的唯一来源是 [implementation-plan-template.md](implementation-plan-template.md)。阅读角色可在计划创建前调查代码并提出计划建议，但不得修改业务逻辑。主编排者核对调研与 proposal 的来源、owner、范围及当前适用性；已有同 owner、同范围且仍适用的结果可复用，只有缺少 owner 输入或范围变化时才补针对性 plan-only proposal。主编排者维护一份整 Feature 计划，不得为每个 worker 复制一份主计划。计划须在第一个实现文件改动前获批。每个 worker 实施前仍须阅读当前获批计划并确认分配范围，但不为已明确的分配另起一轮确认交接。计划深度按风险选择：有界单 owner 工作可以短一些；跨 owner、共享契约、schema/state、数据迁移、安全或高风险行为需要按模板填写条件章节。

手动维护的等效顺序与范围直接记录在运行记录中，不另复制一份 Feature 计划。

并行 item 必须依赖已满足，且文件范围和契约范围都不重叠。计划安排必要的集成验证点，最终集成由主编排者负责。每个实现步骤仍在原位验证；相同模型/会话不必为每个微步骤写重复 handoff。仅在有意义的里程碑、多 agent 汇合、高风险变化或重大偏差时做简短检查点。重大范围、契约、安全或产品决策停下升级；获批的实现调整更新同一份计划并批准受影响部分后继续。

### 准备与阶段交接

环境准备由主编排指定一个负责角色，统一负责设置和清理；其他角色接收现有计划或交接中的准备结果，检查其适用条件后复用，不因角色切换再次安装、构建或建样。详细协议通过 `.factory/local.yaml` 的 `factory_root` 解析到 `skills/hl-workflow-governance/references/execution-preparation.md`。无需另建环境登记表、准备报告或生命周期状态。

代码调研及依赖不变契约的环境准备可以与实现并行。评审角色可提前阅读规则和准备检查，正式评审仍等待来源稳定；最终验收仍在评审通过后执行。准备就绪不能计为业务验收通过。共享环境的配置、启停和基线重置由指定角色管理；消费者按计划执行已获准的测试或业务调用，不为正常使用另作 owner 交接。消费者可能互相干扰时串行使用或隔离状态，保持验收要求的同对象、制品、会话和连续操作条件。

阶段交接传递当前对象、获批计划及变化、适用证据、可用资源的归属与清理责任、剩余必需检查。已读且未变的权威来源引用即可，接手者定向核查变化和疑问，不重做整轮调研。监控优先使用完成通知或可提前唤醒的等待；只能轮询时单次有界、按实际进展检查，不重复启动同一长任务。停滞时先查进程、执行阶段、输出和环境原因，不能把名义 sleep 时长当作可节省的空闲时间。

跨会话交接在原有结构中直接说明关键约束及正式出处、证据实际来源和证明范围、可接续入口、尚未执行或未证的必需项。接续所需的对象/版本/run 身份只记录必要且允许的信息，入口从正式证据记录定位，私有机器信息经忽略配置或允许的当次交接传递。接手者核对当前计划与证据是否满足原约束，不另做“已读确认”或依靠摘要自行放宽条件。

证据来源变化时，保留原事实，记录原因、旧新来源、连续性保留/丢失情况和受影响项，更新同一计划的相关假设/修订及验收结果。重建场景可证明相应能力，不能仅凭同标签、同 ID 或同代码认定原链路延续；原标准允许且有数据沿袭依据的新实例可按实际证明范围接纳。独立评审与分离验收仍须判断受影响部分；来源变更本身不新增用户审批，只有验收、目标或权限实质改变时才走原有决策边界。

## 3. 阅读交接（固定标题）

阅读角色必须输出以下固定标题，缺一不可：

### 阅读交接：范围
任务边界、涉及模块、明确不做什么。

### 阅读交接：权威来源
列出被采信的文档与代码位置，并说明为何采信；列出被判定为过期或非权威的来源。

### 阅读交接：事实与约束
与任务直接相关的稳定事实、接口契约、数据归属、适用约束块。

### 阅读交接：风险与未决问题
风险类别、影响面、需要谁确认；未决问题不得用假设替代。

### 阅读交接：实现入口
建议的最小实现路径、首个改动点、需要的验证方式。

阅读交接只描述事实与建议，不包含实现改动；以上五节承载 [_blocks/handoff-output.md](_blocks/handoff-output.md) 的通用必需信息，不再嵌套七段。

## 4. 实现交接

实现角色按 [_blocks/handoff-output.md](_blocks/handoff-output.md) 的固定结构输出，必须包含：改动清单、行为变化、验证证据、未决问题、回滚方式、需要评审重点看的部分。实现交接不得声称“已评审通过”。

## 5. 评审交接

评审角色必须拿到当前批准依据：Feature 使用 `implementation-plan.md`，手动维护使用运行记录和已选候选。核对改动是否符合获批 scope、owner/file 边界、依赖和集成安排；依据与实际不一致，或评审期间依据的语义变化影响当前判断时，停止受影响部分并交还主编排者处理；单纯记录或非语义性更正不自动使其他有效结论失效。之后按 [review-agent.md](review-agent.md) 与 [_blocks/review-agent-contract.md](_blocks/review-agent-contract.md) 的固定报告结构输出，明确结论、发现级别、未覆盖项与复审建议。

## 6. 验证交接（固定标题）

验证角色必须输出以下固定标题，缺一不可：

### 验证交接：验证对象
被验证的变更标识、环境、基线与范围。

### 验证交接：验收项覆盖
逐条列出验收项、对应证据、通过/失败/未覆盖；不得合并模糊描述。

### 验证交接：证据
可复现的证据位置与复现方式；证据不足时明确写“证据不足”。

### 验证交接：未覆盖与残余风险
未覆盖项、环境差异、已知限制、需要后续跟踪的事项。

### 验证交接：结论
通过、有条件通过、不通过；有条件通过必须列出条件与责任人。

验证交接不得修改被验证对象；发现问题回到实现或评审阶段。
验证角色使用同一份当前批准依据，逐项确认 Feature 计划结果和验收标准，或手动维护的已选目标与验收标准，都有可复现证据；其他任务按其明确验收范围执行。对象身份与来源变化见[评审门](_blocks/review-gate.md)，证据复用、局部补验和停止条件见[测试与质量门](_blocks/testing-quality-gate.md)。使用以上五节输出，不再嵌套通用七段。

## 7. 冲突处理

- **权威冲突**：两份文档对同一契约给出不同答案时，停止实现，列出冲突点、各自出处与影响，交人类裁决。
- **范围冲突**：任务要求越过 owner 写入范围或项目边界时，停止并转交对应 owner，不自行扩权。
- **评审冲突**：实现与评审对事实判断不一致时，以可复现证据为准；证据不足则升级，不以角色级别压人。
- **验收冲突**：验收标准不可验证或互相矛盾时，回到 goal 阶段重写标准，不得降低标准换取通过。
- **时间冲突**：无法在约束内完成时，优先保证正确性与可回滚性，显式记录未完成项，不交付“看起来完成”的结果。

所有冲突都必须留下书面记录，并写明当前阻塞点与所需决策。
