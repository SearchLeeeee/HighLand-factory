# Changelog

All notable changes to HighLand-factory are documented here. Format: Keep a Changelog; versioning: SemVer.

## [Unreleased]

### Added
- **Coding discipline block** (`templates/workspace/wiki/code-ai/_blocks/coding-discipline.md`): the implementation order and code-quality discipline the workflow previously left implicit — decision in one place, data shape before logic, failing-test-first order, attack the premise, subtract before adding, root-cause fixes, verifiable units, behaviour-level tests, quantitative gates, the three-step refactor, boundary and type discipline, idempotence, dead-code removal, and the closing habits (log, context, cleanup, small commits). It is registered in five places at once (block list, both manifests, the manifest enumeration, the owner profile template) and referenced by `hl-feature-profile-generate`, so feature implementation and review profiles cite it instead of restating it. The block defines *how to write and in what order*; `testing-quality-gate` keeps defining *what to test and at which layer*.
- **Optional `quality-gates` pack** (`packs/hl-quality-gates`, skill `hl-quality-gates`): runs the project's configured complexity (CRAP), structural-duplication and mutation-testing commands, translates their exit codes into review findings instead of inventing a verdict, writes one evidence file per run under `packs.quality-gates.evidence_dir`, and fails closed with a named key when no tool group is configured. It documents three preconditions it cannot paper over: the mutation tool needs symlink privileges (a Windows host without them fails the probe, not mid-run), the coverage tool installs tooling into the tested project, and none of the three emits JSON — so the pack records command, exit code, output tail and artifact hashes rather than parsing the metric snapshots. It adds no lifecycle state, no second state machine and no second wiki validator.
- **Worktree lifecycle rules** (`hl-workflow-governance/references/worktree-lifecycle.md`): one governed list of when a Feature worktree and its branch may be reclaimed, when they must be kept, and what the report must contain. `hl-feature-orchestrator` now references it instead of leaving cleanup to an unspecified follow-up, and still never deletes unmerged work.
- **Context discipline** (`hl-feature-orchestrator`): the main thread keeps decisions, approved scope and evidence locations; bulk reading, discovery and implementation stay with subagents, and large files are not read end to end in the main thread.
- **AI-guided quickstart** (`prompts/quickstart.md`): a self-contained bootstrap prompt the user hands to an agent. It makes the agent read the factory docs, install the engine, conduct the P0 interview one decision at a time, dry-run then apply `init`/`adopt`, repair gates, record the baseline and hand off the next step.
- **README full-workflow walkthrough**: end-to-end example from requirement intake to long-term wiki authority switch, with Mermaid diagrams for the quickstart path, the two workflow lanes, the full Feature sequence, the lifecycle state machine and the quick-change escalation path.
- **Parallel development choice at discussion startup** (`hl-feature-discuss`): when a sibling Leaf Feature is dependency-ready, has no blocking child and has disjoint owner, file and contract scope, the skill asks whether to work in the shared checkout or in a dedicated git worktree, and records the answer in the `## Parallel development` workbench section.
- **Worktree mode** (`hl-feature-orchestrator`): the recorded worktree choice is verified, created under `.factory/worktrees/<feature-id>` on branch `feature/<feature-id>` with a `check-ignore` precondition, and used as the subagents' implementation root. Merging it back to `repo.default_branch` is a separate authorized operation that is offered only after the Feature reaches `ready-to-merge / ready`.
- **Implementation goal discipline** (`hl-feature-orchestrator`): entering the implementation environment sets one continuous session goal to advance the Feature to `ready-to-merge / ready`, updated only when evidence changes status and completed only after that transition is recorded and the workspace gate passes.
- **Session boundary between discussion and implementation**: `hl-feature-discuss` ends at `code-ai-profiles / completed` and emits exactly one copyable, self-contained prompt that starts `$hl-feature-orchestrator` in a new session (workspace paths, must-read documents and profiles, confirmed conclusions, deferred questions, parallel development choice, mandatory end state, prohibitions). `hl-feature-orchestrator`, `hl-feature-profile-generate` and `hl-feature-progress` follow the same prompt contract, so the implementation session needs no chat history.

### Changed
- **Commit boundaries are governed in one place**: `hl-workflow-governance/references/commit-boundaries.md` now lists every workflow point where a commit is allowed — initialization, sealed decomposition, discussion documents, Code AI profiles, frozen implementation, passed review, acceptance closure, sealed Initiative integration evidence, per-Feature wiki-merge closure, and quick-change completion — with the gate that must already pass and what the commit may contain. `hl-feature-orchestrator` no longer forbids committing before `ready`; it names the three points inside one implementation session and the rules common to all of them. `packs/hl-commit`, the generated `commit-granularity` block, the feature-workspace README, the skill catalog, the skill contract and the README walkthrough restate the same list.
- **Freeze-then-seal is now explicit**: implementation is committed first to obtain the revision that review, verification and Initiative integration run against, and the evidence naming that revision is committed afterwards. Evidence roots live inside the repository, so running the checks first dirties the tree and destroys the next run's reproducibility baseline.
- **A commit authorization is never a push authorization**, and no commit boundary implies a push. The boundary list adds no lifecycle state, schema field or state-machine branch; the core workflow still runs with `packs.enabled: []`.
- **Parallel Feature work has no numeric cap**: `workflow.max_parallel_features` was removed from the config contract, the generated workflow profile, the templates, the example answers and every skill that restated it. Concurrency is now gated only by real conditions — satisfied `depends_on`, no blocking child, and non-overlapping owner, file and contract scope — with one dedicated git worktree per Feature providing code isolation. A configured number was a scheduling hint that no gate enforced, so it invited a false sense of control; it also defaulted differently in `DEFAULT_CONFIG` (1) and the readable spec template (3).
- `workflow` config validation now rejects unknown `workflow` keys instead of silently accepting them, so a leftover `max_parallel_features` in an existing `factory.yaml` fails closed with a named repair instruction rather than being ignored. `workflow.scope_gate.enabled` and `workflow.scope_gate.split_default` are now type-checked too.
- README quick start now points at `prompts/quickstart.md`; the manual CLI path moved to a fallback subsection.
- README repository structure and documentation index list `prompts/`; minimal example points at the prompt file.
- The leakage guard now also scans `prompts/`, so bootstrap prompts cannot become a project-fact backdoor.
- `templates/workspace/.gitignore` and the adopt/init `.gitignore` block now ignore `.factory/worktrees/`, so a dedicated worktree is never committed as a nested tree.
- The feature-workspace README, schema, `.factory/README.md`, `hl-workflow-governance` entry point and contract, `hl-feature-progress`, the skill catalog, the architecture and skill-contract layout maps and the README walkthrough now restate the worktree choice, the no-merge-before-`ready` rule, the one-goal discipline and the discussion/implementation session boundary.

## [0.1.0] - 2026-10-22

First usable version: greenfield init + split-mode adopt, core feature lifecycle, machine gates, doctor/upgrade, installer and CI guards.

### Added
- **Engine CLI** (`engine/factory.py`): `init`, `adopt`, `doctor`, `upgrade`, `status`, `resolve`, `gate`.
  - config validation, template rendering with scalar/generated placeholders, custom wiki/code folder mapping, owner profile overrides, generated-file hashing, version-range checks.
  - `init`/`adopt` write `.factory/factory.yaml`, `.factory/local.yaml`, `.factory/state.json`, `wiki/governance/init-record.md`, baseline evidence; adopt preserves existing docs, appends `.gitignore` machine-state entries and links generated files into the nearest MOC so the wiki gate stays valid.
- **Workspace templates** (`templates/workspace/`): wiki authority skeleton (README/00–03, domain MOCs, governance digest, feature workspace + schema, quick workspace, code-ai profiles/blocks/manifests), root README/AGENTS/CLAUDE, `.factory` docs, `code/` seed.
- **Adopt code-analysis phase** (`hl-factory-init` + `references/adopt-code-analysis.md`): read-only subagents analyze the existing codebase in slices (repo map, core logic, data contracts, operations, tests, security/privacy, domain glossary); the main session synthesizes an evidence-based wiki baseline (`architecture/overview.md`, `domain/overview.md`, `implementation/overview.md`, `testing/overview.md`, `governance/runtime-and-operations.md`), updates `project-facts.md` and the authority map, and validates the wiki gate. Analysis notes stay gitignored under `.factory/analysis/`.
- **Generic skills** with the `hl-` prefix (collision-safe): `hl-factory-init`, `hl-factory-doctor`, `hl-factory-upgrade`, `hl-feasibility-grill`, `hl-feature-workspace`, `hl-feature-discuss`, `hl-feature-profile-generate`, `hl-feature-orchestrator`, `hl-feature-progress`, `hl-workflow-governance`, `hl-initiative-merge`, `hl-wiki-merge`, `hl-history-trace`, `hl-quick-change`.
- **Machine gates** (project-agnostic): feature-workspace state machine, long-term wiki validator, merge inventory, history trace.
- **Packs**: config ids `commit`, `dev-runtime`, `remote-verify`; installed skills `hl-commit`, `hl-dev-runtime`, `hl-remote-verify` (opt-in, config-driven).
- **Installer** (`install/install.ps1`, `install/install.sh`): bootstraps a PyYAML venv, writes `bin/factory`, links skills/packs into agent roots, refreshes `local.yaml`, supports `--no-skills` / `--skills-root` / `--with-packs`.
- **Upgrade script** (`install/upgrade.ps1`, `install/upgrade.sh`): optional `git pull --ff-only`, engine refresh, agent skill/pack re-link with stale-link cleanup, optional work-repo refresh and generated-file upgrade.
- **Docs**: architecture, skill contract, init questionnaire, customization, upgrade/drift, FAQ, skill catalog, adopt example.
- **CI**: leakage guard over generic assets, engine tests (init smoke + both gates), machine-gate script tests.

### Verified
- `factory init` → `doctor` → `gate all` green on a scratch work repo (engine test suite).
- Split-mode adopt dry-run and full adopt on a **temporary copy** of an existing two-repo project: 0 gate errors, generated files linked into existing MOCs, existing docs preserved. No existing repository was modified by the factory during verification.
- 25 engine tests + 49 machine-gate tests pass; leakage guard clean.
