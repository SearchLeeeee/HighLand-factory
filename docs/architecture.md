# Architecture

## 1. Three layers

```text
HighLand-factory (this repo, generic, versioned on GitHub)
  engine/     deterministic CLI: init, adopt, doctor, upgrade, status, resolve, gate
  skills/     agent skills implementing the workflow (no project facts)
  templates/  work-repo skeleton (wiki authority, code-ai, .factory, code/)
  install/    link skills into Codex/Claude/DSH/...; create the `factory` shim
  docs/       concepts, init questionnaire, customization, upgrade, FAQ

<work repo> (one git repository created or adopted by init)
  .factory/factory.yaml   project config: the only source of truth (committed)
  .factory/local.yaml     machine config: factory path, python, ports (gitignored)
  .factory/state.json     init/upgrade bookkeeping (gitignored)
  code/                   implementation
  wiki/                   authority + feature-workspace + code-ai + quick-workspace
  AGENTS.md / CLAUDE.md   agent entry: load config -> workflow profile -> skill
```

The factory repo contains **no project facts**. The work repo contains **all** project facts. Skills are generic behaviour; configuration is project data.

## 2. Why a fixed layout instead of a token-rendering system

The legacy setup rendered `${TOKEN}` values into skill copies at install time. That works for one machine with one project, but it has two fatal properties for a reusable factory:

1. Token values are machine-scoped, not project-scoped. Two work repos on one machine cannot carry different repositories, Python interpreters or wiki roots without editing the machine file and re-rendering.
2. The moment a skill file contains a token it stops being a single physical copy and becomes a generated artifact, so editing, syncing and drift detection become three separate problems.

HighLand-factory instead standardises the layout (`code/` + `wiki/` and fixed paths inside them) and moves variable **values** into `.factory/factory.yaml`. Skills reference relative paths and read the generated `wiki/governance/workflow-profile.md` for values. No template substitution is needed for skill contents, so skills stay single-copy, cross-agent and upgradeable.

If a project insists on different folder names, only `repo.code_path` and `repo.wiki_path` move; all other wiki-internal paths stay fixed. This is deliberate: a small contract is what makes the workflow reusable.

## 3. Repository modes

| Mode | Layout | Use |
| --- | --- | --- |
| `mono` (default) | one repo, `code/` and `wiki/` tracked together | new projects; simplest possible topology |
| `split` | work repo tracks `wiki/`; `code/` is a separate git repo at `repo.code_external` | existing two-repo projects (e.g. public code + private design repo) |
| `submodule` | not supported in v0.1 | deferred; avoids a second update protocol |

Trade-offs of `mono`: code and wiki share visibility and history; CI must use path filters so wiki-only changes do not rebuild code; a public code repo cannot carry a private wiki. `split` exists exactly for that case and is a first-class mode, not a hack.

## 4. Configuration contract

`factory.yaml` sections: `schema`, `factory`, `project`, `repo`, `owners`, `commands`, `verification`, `workflow`, `security`, `agents`, `packs` (see the template and `docs/skill-contract.md`).

Rules:

- Unknown keys are rejected by `factory doctor` (fail closed) unless prefixed with `x-`.
- Required values: `project.name`, `project.slug`, `project.language.docs`, `repo.mode`, `repo.default_branch`, `repo.code_path`, `repo.wiki_path`.
- `repo.mode: split` additionally requires `repo.code_external`.
- Paths are relative to the work root except `repo.code_external`, which may be absolute.
- Empty `commands` entries are allowed at init time but produce doctor warnings; a project should not pass `factory doctor --strict` with empty test/verify commands.
- Secrets never live in `factory.yaml`; only references and policy do.

`local.yaml` holds machine facts only: `factory_root`, `python`, `node`, `ports`, `env`. It is generated by `factory init`/`install` and gitignored.

## 5. Init and adoption

`$hl-factory-init` (skill) is the conversation; `factory init` (engine) is the deterministic writer. The split keeps the agent responsible for requirements, architecture and policy, while the engine guarantees a valid, reproducible skeleton.

- `new`: create a greenfield work repo from templates.
- `adopt`: attach the factory to an existing repo (usually `split` mode with an existing code repo and wiki root); never rewrite existing docs; fill only missing skeleton files, config and digest; report every skipped/conflicting path. **Adopt is opt-in**: the factory never modifies an existing repository unless the user explicitly runs adopt on it. The v0.1 verification used a temporary copy.
- `attach`: a work repo that already has `.factory/factory.yaml`; route to `$hl-factory-doctor` instead.

Every init produces `wiki/governance/init-record.md` containing the answers, detected facts, assumptions, generated-file hashes and the exact engine version. This is the provenance baseline for later "why is this configured like this" questions.

Idempotency: every write is planned first (`--dry-run`, machine-readable), then applied. Existing files are skipped unless they are recorded generated files and `--force` is given. A failed init can be re-run; `factory doctor` reports residual state.

## 6. Gates, not prose

The executable gates stay executable:

- `skills/hl-feature-workspace/scripts/feature_workspace.py` is the only lifecycle state machine (validate, report, transition, decomposition, merge readiness, integration handoff/result).
- `skills/hl-wiki-merge/scripts/validate_llm_wiki.py` is the only long-term wiki content gate (home, navigation depth, link integrity, isolation from feature/quick workspaces).
- `skills/hl-history-trace/scripts/trace_feature_history.py` is the only provenance reader.
- `skills/hl-wiki-merge/scripts/inventory_llm_wiki_merge.py` is the deterministic merge inventory.

Skills call these through `factory gate ...` or directly with explicit paths. Prose and code must not drift: when a rule changes, the owning script, its tests, the schema doc and the affected skills change together (see `docs/customization.md`).

## 7. Upgrade and drift

- `factory.yaml:factory.version` pins a compatible engine range.
- `.factory/state.json:generated_files` stores the SHA-256 of every generated file at write time.
- `factory upgrade --check` compares the current factory version and template set with the recorded state, and classifies files as unchanged / locally edited / missing.
- `factory upgrade --apply` rewrites generated files that are unchanged and still match the new template; files edited by the project are reported, never overwritten.
- User-edited authority documents (`wiki/00-spec.md`, `wiki/02-file-authority-map.md`, project facts, owner profiles after the first generation) are never regenerated; only the digest and generated indexes are.

## 8. Packs

Core workflow is project-agnostic. Environment- or vendor-specific behaviour ships as opt-in packs:

- `commit` (git policy: repo mode aware, granular commits)
- `dev-runtime` (start/stop/restart local services and health checks)
- `remote-verify` (run one commit through an isolated/remote clone and return a machine verdict)

Packs read the same config and declare their own required keys under `packs.<id>`; they are installed only when listed in `packs.enabled`. Domain skills for specific vendors or verticals are not part of this repository.

## 9. CI guards

The repository CI must prove three things:

1. Engine unit tests pass and the engine compiles on the minimum Python.
2. A temporary work repo can be generated from templates and passes `factory doctor` plus both machine gates (template smoke test). This is what prevents "the validator passes a one-file wiki" from hiding an incomplete skeleton.
3. No project leakage: a grep over generic assets finds none of the forbidden names/paths/tokens listed in `docs/skill-contract.md`.

## 10. Deliberate non-goals for v0.1

- No GUI. The skills are the interface.
- No multi-project registry inside the factory; each work repo is self-describing.
- No automatic git push or GitHub repository creation; init prepares a local repo and prints the exact remote commands, requiring user authorization.
- No vendor-specific domain packs.
- No second lifecycle state machine, ever.
