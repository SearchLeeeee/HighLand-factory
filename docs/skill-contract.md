# Skill Contract

This document is normative for every skill shipped by HighLand-factory. A skill that violates it is a defect.

## 1. Three configuration layers

| Layer | Path | Committed? | Owner | Purpose |
| --- | --- | --- | --- | --- |
| Project config | `<work>/.factory/factory.yaml` | yes | init / user | Single source of truth for project identity, layout, owners, commands, gates, security, packs. |
| Machine config | `<work>/.factory/local.yaml` | no (gitignored) | `factory install` / `factory init` | Machine-scoped values: factory checkout path, Python with PyYAML, Node, ports, env. |
| Workflow digest | `<work>/wiki/governance/workflow-profile.md` | yes | generated by engine | Human/agent-readable digest of the effective config. Every skill reads this first. Regenerated from `factory.yaml`; do not hand-edit. |

Machine-scoped and project-scoped values never mix. A skill must never contain an absolute path, a drive letter, a project name, a repository name, or a machine token.

## 2. Fixed layout contract

Paths are fixed relative to the **work repo root** (`<work>`). Config may rename the two top folders only through `repo.code_path` / `repo.wiki_path`; skills should use the resolved layout section in `workflow-profile.md`, not assume the literals.

```text
<work>/
  .factory/factory.yaml
  .factory/local.yaml          # gitignored
  .factory/state.json          # gitignored, init/upgrade bookkeeping
  code/                        # implementation (mono mode)
  wiki/                        # long-term authority root
    README.md                  # root MOC
    00-spec.md
    01-reading-guide.md
    02-file-authority-map.md
    03-current-decisions.md
    governance/workflow-profile.md
    feature-workspace/         # isolated lifecycle workspace
      registry.yaml
      README.md
      schema/feature-workspace-schema.md
      initiatives/
    quick-workspace/           # isolated quick-change records
    code-ai/                   # agent profiles + blocks + manifests
  AGENTS.md
  CLAUDE.md
```

`repo.mode`:

- `mono` (default): one git repository, both `code/` and `wiki/` tracked together.
- `split`: the work repo tracks `wiki/`; `code/` is a separate git repository referenced by `repo.code_external` (absolute or relative to the work root). This is the compatibility mode for projects that already have two repositories.

## 3. Skill step 0 (mandatory preamble)

Every skill starts its execution with this reasoning step, even if it only reads state:

1. Read `<work>/.factory/local.yaml`. If missing or unreadable, stop and tell the user to run `$hl-factory-init` (or `factory init`).
2. Resolve:
   - `FACTORY_ROOT` = `local.yaml:factory_root`
   - `PYTHON` = `local.yaml:python`
   - `WORK_ROOT` = the work repo root (current git top-level or the directory containing `.factory/`)
3. Read `WORK_ROOT/wiki/governance/workflow-profile.md`. It defines project language, layout, owners, commands, gates and security boundaries. If missing, stop and run `$hl-factory-doctor`.
4. Run gates through the engine instead of composing paths by hand:

```bash
<PYTHON> <FACTORY_ROOT>/engine/factory.py doctor   --work <WORK_ROOT>
<PYTHON> <FACTORY_ROOT>/engine/factory.py resolve  --work <WORK_ROOT> --json
<PYTHON> <FACTORY_ROOT>/engine/factory.py gate workspace --work <WORK_ROOT>
<PYTHON> <FACTORY_ROOT>/engine/factory.py gate wiki      --work <WORK_ROOT>
```

5. If the project's `workflow-profile.md` or `factory.yaml` disagrees with what the user is asking, route to `$hl-workflow-governance` instead of improvising.

A skill must fail closed: missing config, missing project profile, failing gate, or unresolved language policy stops the skill with a concrete repair instruction.

## 4. Project values a skill may rely on

Read these from `workflow-profile.md` / `factory.yaml`; do not invent them:

| Section | Values |
| --- | --- |
| project | name, slug, one-liner, stack, doc/code/commit language, license, visibility |
| repo | mode, default branch, code path, wiki path, code external path, commit format |
| layout | code root, wiki root, feature-workspace root, quick-workspace root, code-ai root |
| owners | id, title, owned paths, profile path |
| commands | setup, build, lint, typecheck, test, e2e, dev, verify |
| verification | baseline evidence path, evidence root, isolated environment policy |
| workflow | scope gate on/off, split default, quick change, review required, verification separated, merge authorization, initiative integration required, max parallel features |
| security | forbidden operations, sensitive classes, secrets file |
| agents | platforms, review model, verification model |
| packs | enabled, disabled |

If a needed value is empty, the skill must ask the user once and then route to `$hl-workflow-governance` to persist it; it must not silently default.

## 5. Skill naming

All skill directories and their `name:` fields carry an `hl-` prefix. The agent skill spec
requires lowercase kebab-case, so the prefix is written `hl-` (meaning the same as an `HL-`
prefix). This avoids collisions with other workflows installed in the same agent. Legacy
names from pre-factory setups are intentionally not listed here; migrate by role, not by name.

| Skill | Role |
| --- | --- |
| `hl-feasibility-grill` | Technical feasibility stress test before decomposition |
| `hl-feature-discuss` | One Leaf Feature: confirmed conclusions, implementation docs, profile inputs |
| `hl-feature-workspace` | The only lifecycle state machine and schema gate |
| `hl-feature-profile-generate` | Compose executable Code AI profiles per Feature |
| `hl-feature-orchestrator` | Dispatch owners, plan approval, review/acceptance gates |
| `hl-workflow-governance` | Routing, invariants, workflow maintenance |
| `hl-initiative-merge` | Initiative-level integration acceptance before merge |
| `hl-wiki-merge` | Semantic wiki merge, validator gate, retained history |
| `hl-feature-progress` | Read-only progress/blockers/next-session prompt |
| `hl-history-trace` | Isolated provenance lookup through tombstones |
| `hl-quick-change` | Bounded bugfix/adjustment on-ramp with escalation |
| pack `commit` (skill `hl-commit`) | Optional git policy skill |
| pack `dev-runtime` (skill `hl-dev-runtime`) | Optional service restart/health skill |
| pack `remote-verify` (skill `hl-remote-verify`) | Optional remote/isolated verification skill |

## 6. Generated files

Files generated by the engine carry a first-line marker:

```html
<!-- GENERATED by HighLand-factory <version> from <template>; do not hand-edit. -->
```

Skills must not edit generated files directly. To change them: edit `.factory/factory.yaml`, then run `factory upgrade --work <work>` (or re-run the relevant init step), then `factory doctor`.

Generated files include at least: `wiki/governance/workflow-profile.md`, `wiki/governance/init-record.md`, `wiki/code-ai/<owner>-agent.md` (initial profiles), `wiki/code-ai/_manifests/<owner>.yml`, `.factory/factory.yaml` (initial), `.factory/state.json`.

## 7. Language

- `project.language.docs` controls user-facing wiki prose and discussion documents.
- `project.language.commit` controls commit subject/body language.
- Stable IDs, paths, YAML keys, lifecycle enums, skill names and verdict labels stay ASCII in their required form regardless of language.
- A skill that talks to the user matches the user's language, not the configured doc language, unless the configured policy explicitly says otherwise.

## 8. Forbidden in generic assets

Checked by CI over `skills/`, `engine/`, `templates/`, `install/`, `packs/`, `prompts/`:

- private project, workspace, vendor, or model-tier names (the guard keeps a private,
  obfuscated pattern list; this repository does not spell them out)
- absolute paths or drive letters (`C:\`, `D:\`, `/home/`, `/Users/`)
- machine tokens (`${SKILLS_ROOT}`, `${WORKSPACE_ROOT}`, `${REPO_CODE}`, `${REPO_DOCS}`, `${WIKI_ROOT}`, `${PYTHON}`)
- hardcoded ports, hostnames, or repository URLs

Project-specific knowledge belongs to the generated work repo, or to an opt-in pack, never to the core skill/template surface.

## 9. Template placeholders

Work-repo templates under `templates/workspace/` are rendered once by the engine at init/upgrade.

| Form | Meaning |
| --- | --- |
| `{{project.name}}`, `{{project.slug}}`, `{{repo.mode}}`, ... | scalar value from `factory.yaml`, dotted path |
| `{{generated:date}}`, `{{generated:factory_version}}` | engine facts |
| `{{generated:<name>}}` | multi-line Markdown fragment produced by `engine/factorylib/generated.py` |
| `{{owner.<field>}}` | owner field, only valid in `templates/owner-templates/*` and `_manifests/owner.yml.tmpl` |

Unknown placeholders are a hard render error. Adding a generated fragment requires updating `GeneratedBlocks`, this contract, and the template that uses it.

Owner profiles and owner manifests are generated once per configured owner. An owner may set `profile:` in `factory.yaml` to reuse an existing project profile path instead of the default `wiki/code-ai/<id>-agent.md`.

## 10. Pack contract

- A pack lives under `packs/hl-<id>/SKILL.md` (skill name `hl-<id>`), is opt-in via `packs.enabled: [<id>]` (the config id stays unprefixed), and must fail closed with a named config key when disabled or misconfigured.
- A pack reads the same `.factory/local.yaml` + `wiki/governance/workflow-profile.md` and never requires core skills to depend on it.
- A pack must not add lifecycle states, a second state machine, or a second wiki validator.
- Packs are installed only with `install --with-packs` (or by linking `packs/hl-<id>` manually); the default install is core-only.
